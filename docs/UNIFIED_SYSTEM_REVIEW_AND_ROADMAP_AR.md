# التقرير الموحد لمراجعة Yemen Smart وخارطة التطوير

**الحالة:** مراجعة أولية مدمجة مع تحديث جرد ساكن بخمس طبقات، وليست جردًا نهائيًا لكل شاشة وجدول وعلاقة.
**الغرض:** توحيد تقرير المستخدم المقدم في المحادثة مع دراسات MQL5 وجودة التدريب المرفقة، وربط الاستنتاجات بما أمكن التحقق منه في نسخة المشروع المحلية.
**تاريخ إعداد التقرير:** 28 أكتوبر 2026.

## 1. الملخص التنفيذي

يمتلك Yemen Smart نواة تطبيق قائمة تشمل لوحة Next.js، خدمات Python مستقلة، جسرًا محليًا إلى MetaTrader 5، واجهات API، Redis للتدفق/التخزين المؤقت، ومخزن DuckDB للبيانات. وتوجد صفحات تشغيلية قائمة مثل Dashboard وHistory وStrategies وModels وModel Comparison وSettings، إضافة إلى لوحات فرعية. لذلك ينبغي أن يبدأ التطوير بتحسين ما هو موجود وربطه بعمليات صحيحة، لا بإعادة تصميم النظام أو إنشاء لوحة موازية.

أكد الفحص السابق عدم وجود صفحة أو مسار متكامل لاستيراد CSV تاريخي؛ فصفحة History الحالية لسجل الصفقات وتصديره، وليست واجهة لاستيراد شموع سوق. عند الحاجة إلى هذا العمل، يكون الخيار الأول توسيع قسم History أو شاشة البيانات القائمة بأسلوب متوافق مع التصميم الحالي، ولا تُنشأ صفحة مستقلة إلا إذا أثبت الجرد أن تدفق الاستيراد لا يمكن دمجه استخداميًا في واجهة قائمة.

الأولوية الفنية ليست زيادة تعقيد النموذج، بل سلامة المصدر والتوقيت والرمز وحالة إغلاق الشمعة وتعريف الهدف والتقييم الخارجي. وتظهر المراجعة المرفقة مخاطر محددة في تحويل توقيت MT5، وفقد التيكات بين دورات الاستطلاع، ووسم التدريب، والشموع المفتوحة، والتقييم الزمني، والتكاليف. كما وجدت مراجعة محلية سابقة أن التدريب الآلي في خدمة ML يمكن أن يبدأ وفق عتبة بيانات وفترة انتظار، ولذلك يجب عزل البيانات التاريخية عن التدفق الحي وعدم السماح للاستيراد بتشغيل التدريب ضمنيًا.

## 2. حدود المراجعة ودرجة الثقة

جرى الاطلاع على التقارير الفنية المرفقة: مراجعة معمارية بيانات MQL5، خطة تكامل MQL5، دراسة جودة تدريب ML، وسياسة مصادر البيانات. كما تمت مراجعة الأدلة السابقة من المستودع وفحوص قراءة محدودة على النسخة المحلية. دراسة التدريب المرفقة تصف لقطة مستودع عند commit `2bdabf0b0f84d7416253d4de6cbbc1086d5be2d3`؛ وقبل بدء التطوير المحلي كانت هناك تعديلات غير ملتزمة في `requirements.txt` و`services/nexus_data/main.py` و`services/nexus_executor/mt5_executor.py`. حُفظت هذه التعديلات دون تغيير.

لم يُنفذ جرد شامل لكل route أو صفحة أو جدول أو مفتاح أجنبي. بعد إعداد النسخة الأساسية من التقرير، أُجريت مراجعة ساكنة إضافية للواجهة وAPI والتخزين وجسر MT5 والتدريب، وشُغّلت أربعة اختبارات وحدوية حتمية لمحوّل UTC واختيار الشمعة المغلقة مع فحص الترجمة البرمجية. لم يُشغّل كامل pytest (غير متوفر في بيئة الاختبار)، أو خدمات التطبيق، أو MT5، ولم تُكتب قاعدة بيانات. لذلك لا تمثل النتائج شهادة باكتمال النظام أو تأكيدًا لسلوك النشر؛ يجب استكمال الجرد والاختبارات قبل migrations أو تغيير سلوك التشغيل.

**التغيير المنفذ بعد التقرير الأساسي:** أصبح `mt5-bridge/bridge.py` يحوّل epoch من واجهة MT5 Python مباشرة إلى ISO-8601 UTC دون طرح offset مقاس من tick، ويستبعد الشمعة الجارية من القراءة الحية وبذر التاريخ. أزيلت معايرة الساعة التي تقارن آخر tick بوقت النظام، وحُدّث دليل الجسر وملفا الإعدادات. توجد أدوات نقية في `mt5-bridge/time_utils.py` وأربعة اختبارات في `tests/test_mt5_time_utils.py`. اجتازت `py_compile` و`unittest`؛ لم يُختبر اتصال حي مع MT5 ولم تُشغّل مجموعة pytest الكاملة.

**معالجة Label Leakage المحلية:** أضيف `services/nexus_ml/training_data.py` لتعريف schema v2، تنقية X، تحديد هدف `next_observed_adjacent_bar_close_direction`، واختبار timestamp والفاصل. يحتفظ المستهلك بآخر بار كعينة معلقة في Redis؛ لا يكتبها للتدريب إلا بعد وصول البار المجاور التالي، ويهمل التعادل والفجوات والوقت غير الموثوق. منتج features يرسل وقت البار من مصدره ولا يمنح `bar_timestamp` التدريبي إلا بعد انقضاء فاصل الشمعة. صار جلب التدريب يتجاهل السجلات legacy ويرتب بياناته؛ مدرب WalkForward يعيد التنقية، يفرض أسماء ميزات، يpurge صفًا عند حد split، ويسجل تقييم XGBoost على validation خارجي. تحفظ metadata `training_schema.json`، ويرفض `ModelEnsemble` تحميل ملفات قديمة أو غير متطابقة، مع استخدام fallback القائم عند غياب نموذج اتجاه آمن. أضيفت 8 اختبارات وحدوية ناجحة وفحص ترجمة واستيراد داخل `.venv`؛ لم يُنفذ تدريب فعلي.

لا يحذف هذا التغيير سجلات Redis القديمة أو ملفات النماذج القديمة؛ تُترك كما هي لكن لا تُستخدم في تدريب جديد أو تحميل ensemble دون metadata. كما لا يثبت وحده أن كل feature مشتقة من بيانات متاحة لحظة القرار، خصوصًا revision التاريخية للأخبار/الاقتصاد أو cross-asset snapshots؛ يلزم اختبار prefix-causality وتدقيق point-in-time منفصل قبل اعتماد الأداء.

## 3. الوضع الراهن: نقاط قوة وفجوات مثبتة/محتملة

### 3.1 نقاط القوة

- واجهات قائمة ومتسقة بصريًا، بما فيها لوحة Dashboard وHistory وStrategies وModels وModel Comparison وSettings؛ هذه هي نقطة الانطلاق للتطوير.
- فصل خدمات Python بحسب الوظيفة، مع nexus-data وnexus-api وnexus-features وnexus-news وnexus-ml وغيرها.
- وجود جسر MT5 قائم يرسل بيانات سوق وتشغيلًا، ووحدات بيانات وأخبار وتقويم ومؤشرات وأصول مترابطة.
- مخطط OHLCV ومخزن DuckDB وقنوات Redis يتيحان أساسًا لإضافة تاريخ مستورد دون بناء منظومة موازية، شريطة تحديد ملكية الكتابة ومطابقة المخطط.
- توثيق تقني مرفق غنيّ يحدد مراجع MQL5 الرسمية ومخاطر التوقيت والتسرب الزمني وطرق التحقق.

## 4. قرار تصميم قاعدة البيانات

لا توصي التقارير جميعها بترحيل فوري. مراجعة معمارية MQL5 تعرض PostgreSQL/TimescaleDB كخيار معماري مناسب عند توسيع جمع التيكات والتعدد والاحتفاظ، لكن خطة تكامل MQL5 ودراسة جودة التدريب توصي صراحةً بإبقاء DuckDB/Redis أولًا وإضافة المخطط والحقول والاختبارات، ثم اتخاذ قرار الترحيل بناءً على حجم البيانات وعدد الكتّاب وقياسات الأداء.

التوصية الموحدة: **المرحلة الحالية لا تغيّر محرك التخزين.** أنجز جرد المخطط ومصادر الحقيقة، وصمم migrations متوافقة مع الوضع الموجود، واختبر الاتساق والتكرار والقراءة. سجّل قرارًا معماريًا (ADR) بمقاييس قابلة للقياس قبل أي انتقال إلى PostgreSQL/TimescaleDB. إذا تقرر الانتقال لاحقًا، يُنفّذ كمسار ترحيل مستقل مع مزامنة/تحقق/خطة رجوع، لا ضمن استيراد CSV.

وبخصوص العلائقية، يُفصل بين: البيانات التشغيلية الحية والذاكرة/التدفق، السجل التاريخي الخام غير القابل للاستبدال، والجداول المشتقة/التقارير. لا يُفترض أن Redis سجل دائم أو أن DuckDB وحده يوفر كل ضوابط FK/التزامن المطلوبة؛ يجب توثيق القيود الفعلية في المحرك الحالي قبل تقرير ما يمكن فرضه مباشرة وما يحتاج تحققًا على مستوى التطبيق أو migration.

## 5. التوصية الموحدة بشأن الواجهات

لا يُنشأ منتج واجهة جديد ولا تكرر لوحة قائمة. يبدأ التنفيذ بجرد routes ومكونات التنقل ومصادر البيانات لكل شاشة. ثم:

1. تطوير الوظيفة داخل الشاشة الحالية، ما دام ذلك واضحًا للمستخدم ولا يخلط مهامًا مختلفة.
2. استخدام تبويب أو صفحة فرعية تحت قسم قائم (مثل History للبيانات التاريخية) عند إضافة قدرة جديدة لا يوجد لها موضع حالي.
3. إضافة شاشة مستقلة فقط لوظيفة جديدة ذات تدفق عمل مستقل، مع توثيق سبب عدم ملاءمة شاشة قائمة.
4. ربط القوائم والجداول المرجعية بمصدر مرجعي موحد ذي تحديث/مالك واضح.
5. ربط الشاشات التشغيلية عبر API/عقود typed ومعرفات كيانات مشتركة؛ لا تستخدم نسخًا محلية متباينة من نفس البيانات.
6. للواجهة التي لا بيانات لها: لا تملأها ببيانات واقعية مختلقة. إما ربطها، أو بيان سبب عدم التوفر وحالة التنفيذ، أو تعطيلها مؤقتًا بتوثيق؛ أما seed data فتظل في بيئة الاختبار ولا تنتقل إلى الإنتاج.

## 6. المخطط الوظيفي المقترح للبيانات التاريخية

### 6.1 تداول السوق وMT5

- حفظ المصدر الخام/الدفعة، هوية الوسيط والخادم والطرفية والرمز الخام، الرمز القياسي كعلاقة alias غير مدمرة، الإطار الزمني، وقت السوق الخام، وقت UTC الموثوق إن أمكن، وقت الاستلام، أساس الوقت ونسخة التحويل.
- حفظ tick fields كاملة عند جمعها: `time_msc`, bid/ask/last, volume/volume_real, flags, source sequence/batch. لا تدّعِ اكتمال ticks من استطلاع آخر quote.
- حفظ bar fields: OHLC، `tick_volume`، `real_volume`، spread ووحدته، `is_closed`/status ومصدره. لا تدخل bar جارية إلى تدريب كأنها مغلقة.
- التقاط `symbol_info` ومواصفات العقد والجلسات كـsnapshots مؤرخة؛ لا تجعل تطبيع الاسم يزيل الفروقات التجارية بين الوسطاء.
- watermarks وسجل تشغيل الالتقاط والفجوات والأخطاء، مع استرجاع متداخل بعد الانقطاع. الخام append-only، والمشتقات قابلة لإعادة البناء.

### 6.2 الأخبار والاقتصاد والأساسيات والأصول المترابطة

- فصل الخبر، الحدث الاقتصادي، الملاحظة الأساسية/المالية، ومشاهدة سعر الأصل المترابط ككيانات مستقلة.
- لكل قيمة: source/URL أو اسم ملف، unit/currency/frequency، observation/event time، publication/available time، retrieval/received time، revision/vintage، وحالة موثوقية/تقدير.
- تمنع ميزة تاريخية من استعمال معلومة لم تكن متاحة لحظة القرار. تستخدم علاقة زمنية point-in-time على `available_at`، لا مجرد مطابقة وقت الحدث.
- اشتقاق الارتباطات والمؤشرات ضمن pipeline مؤرخ ومُرقّم إصدارًا؛ لا تحفظ ناتجًا مشتقًا على أنه حقيقة مصدرية. تمييز fallback/بيانات اصطناعية صريح، واستبعادها أو اختبارها منفصلة.

## 7. مسار العمل الموحد والمراحل

### المرحلة 0 — جرد وحماية الحالة الحالية

- حصر كل الواجهات والـroutes، كل خدمة/endpoint، مصدر البيانات، الجداول/الأعمدة والفهارس/المفاتيح، عقود DTO، الصلاحيات، والتقارير.
- إعداد مصفوفة تغطية: مكتمل، جزئي، بلا بيانات، غير موصول، أو غير مستخدم؛ مع مالك الواجهة ومصدر الحقيقة وقرار تغطيتها.
- تسجيل baseline للاختبارات والصحة، وحصر الملفات غير الملتزمة؛ حفظ تعديلات المستخدم وعدم الكتابة فوقها.

**قبول المرحلة:** جدول جرد قابل للمراجعة، خريطة علاقات وقرارات للواجهات الفارغة، قائمة فجوات مصنفة حسب أثرها ومخاطرها.

### المرحلة 1 — سلامة التخزين والهوية والتوقيت

- تصحيح/تثبيت مسار التوقيت من مصادر MT5 وفق نوع الواجهة؛ لا تطبيق تحويل مزدوج على أوقات Python الموصوفة UTC.
- توثيق schema الحالية ومصدر الحقيقة والـretention، وإضافة lineage ومواصفات الأداة وحالة إغلاق الشمعة حسب حاجة المخطط.
- تصميم idempotency وتكرار/تصحيح تاريخي بعد قياس البيانات القائمة؛ لا إضافة unique constraint قبل تسوية duplicates ومراجعة migration.
- اختبارات زمنية تشمل UTC epochs وDST ووقت جهاز غير UTC، واختبار فصل الجسر واستعادته من watermark على Demo عند التوفر.

**قبول المرحلة:** الخام يبقى كما استُلم، التحويلات قابلة للتفسير وإعادة البناء، لا تُدمج رموز وسيط مختلف، والبيانات غير المغلقة مميزة.

### المرحلة 2 — تحسين الوظائف والربط في الواجهات القائمة

- وصل عناصر الواجهة الحالية بعقود API موحدة؛ معالجة حالات empty/loading/error وسبب عدم توفر البيانات.
- جرد القوائم المرجعية وربطها بمرجعيات مشتركة؛ إضافة مفاتيح وعلاقات وفهارس ملائمة بعد تدقيق المخطط.
- توحيد المصادقة والتفويض على مستوى الخادم، واختبار الصلاحيات على كل route كتابة/تدريب/إدارة.
- توحيد سجل التدقيق والتقارير مع lineage؛ لا تكرر استعلامات مجزأة متعارضة داخل الصفحات.

**قبول المرحلة:** كل شاشة غير معطلة تُظهر مصدرها وحالتها وتدفقها؛ لا شاشة «نجاح» تخفي فشل backend، وعمليات الكتابة المحمية تختبر 401/403 وتسجيل التدقيق.

### المرحلة 3 — استيراد البيانات التاريخية في الواجهة القائمة

- إضافة تدفق رفع/معاينة/ربط أعمدة/تحقق/تقرير/تأكيد داخل History أو قسم بيانات قائم، دون أثر كتابة في مرحلة المعاينة.
- دعم صادرات MT5 وYemen Smart الموثقة بصيغة CSV/TSV. التحقق من الحجم والرؤوس والقيم والنطاق والتكرارات وعلاقات OHLC والفجوات؛ عرض الفجوات كتحذير لا كإصلاح آلي.
- تسجيل دفعة الاستيراد وبصمة الملف والصفوف والأخطاء. بعد تأكيد المستخدم فقط تحفظ الصفوف المقبولة بدفعة ومعاملة وسياسة upsert معلنة؛ لا بث تاريخ كامل في Redis الحي.
- توضيح المنطقة الزمنية، الرمز/الإطار، وحدة spread، والتمييز بين tick volume وreal volume قبل commit.

**قبول المرحلة:** معاينة لا تغير التخزين؛ الاستيراد المؤكد قابل للتدقيق وإعادة المحاولة دون تكرار؛ لا فقد لحقول المصدر أو تحويل وقت/حجم صامت.

### المرحلة 4 — هدف وخصائص وتقييم تدريب تاريخي منفصل

- كتابة بطاقة هدف تشمل وقت القرار، مصدر ووقت إتاحة الميزات، الأفق، target، سياسة السعر والتكاليف.
- تصحيح تناقض label الحي والهدف المقصود؛ لا تدريب قبل اختبارات الاصطناع والسببية.
- تقسيم rolling/expanding زمني مع تقييم خارجي حقيقي، train-only preprocessing، purge وفق فترات labels، واختبار نهائي محجوب.
- تجارب ablation واحدة التغيير كل مرة: baseline، label، خصائص OHLC، MTF مغلق، ticks/microstructure فقط عند توافرها، ثم بدائل النماذج.
- تقرير metrics يشمل baseline ومعدل الفئة وprecision/recall وAP/PR وlog-loss/Brier ومعايرة عند الملاءمة، إضافة إلى صافي تكلفة التداول/التغطية/التراجع؛ يصرح بالافتراضات والحدود.
- سجل تجارب غير قابل للطمس مع commit/hash بيانات وschema/features/labels وseed والتقسيم والتبعيات والمقاييس. حفظ المرشح دون استبدال champion.

**قبول المرحلة:** لا يتغير النموذج النشط بمجرد التدريب؛ النتائج قابلة لإعادة البناء، وvalidation/test لم يشاركا في الملاءمة أو اختيار النموذج.

### المرحلة 5 — ربط الوحدات والتقارير والتشغيل الآمن

- سيناريوهات E2E تغطي إدخال البيانات، تحققها، ربطها بالرمز، استعلامها، إعداد الخصائص، التقرير، والتدريب المرشح.
- اختبار الصلاحيات والتدقيق والتزامن والأخطاء وإعادة المحاولة/التراجع.
- نشر candidate في shadow/paper ومقارنته مع champion على مدخلات نفسها. الموافقة والترقية والعودة للإصدار السابق إجراءات منفصلة وصريحة.
- اتخاذ قرار مخزن البيانات على أدلة قياس. ترحيل PostgreSQL/TimescaleDB خارج هذه المراحل إلا إذا أقر قرار معماري منفصل.
- تسليم دليل فني، دليل مستخدم، مخطط علاقات، بيانات seed الاختبارية إن وجدت، وخطة صيانة واحتفاظ ونسخ احتياطي.

## 8. قواعد حاكمة للتنفيذ

- لا تُطلق عملية تدريب بسبب رفع ملف أو استيراده، ولا تحرك بيانات تاريخية إلى Redis history الحي.
- لا ترقية تلقائية إلى champion، ولا تنفيذ تداول أو تغيير إعداد تداول ضمن هذا النطاق.
- لا بيانات seed في الإنتاج، ولا تقدير/ملء/تحويل صامت للحقول أو الوقت أو الوحدات.
- لا تغييرات على قاعدة البيانات دون فحص التكرارات والمخطط وخطة migration/rollback واختبار على نسخة اختبارية معزولة.
- لا تعديل على ملفات المستخدم المعدلة حاليًا دون مراجعتها ودمجها بشكل محافظ.
- لا نشر أو دفع إلى GitHub ضمن هذه المراجعة؛ إعداد التقرير والخطة محلي فقط. أي التزام GitHub دوري/متكرر يحتاج تعريفًا صريحًا للفرع والوتيرة والمحتوى وصلاحية موثقة، ولا يستخدم token مكشوف سابقًا.

## 9. القرارات المطلوبة قبل التنفيذ

1. اعتماد خطة الجرد والتطوير التدريجي، وتحديد أولوية أول مجموعة شاشات/خدمات.
2. تأكيد أن البداية تكون بتحسين شاشة History القائمة أو قسم قائم، لا بإنشاء لوحة موازية؛ يمكن إنشاء فرع/تبويب عند الحاجة الوظيفية فقط.
3. اعتماد إبقاء DuckDB وRedis في المرحلة الحالية، مع إعداد ADR مستقل إذا أظهرت القياسات ضرورة PostgreSQL/TimescaleDB.
4. تحديد صلاحية من يؤكد استيراد البيانات ويبدأ التدريب ويعتمد ترقية نموذج.
5. تحديد معنى وقت MT5 للملفات القديمة: بيانات Python موصوفة UTC أم وقت سيرفر خام؛ عدم تحويلها بأثر رجعي دون clock profile موثق.
6. تحديد مصادر بيانات الأخبار/الاقتصاد/الأساسيات المرخصة وتوافر تاريخ `available_at` وrevisions.
7. تحديد هدف التدريب والأفق والتكاليف ومقاييس القبول. لا يمكن اعتبار «التدريب بجميع مراحله» هدفًا فنيًا محددًا دون بطاقة target.
8. إذا كان المقصود تحديث GitHub تلقائيًا أو باستمرار، تحديد هل المطلوب commits محلية أم push إلى مستودع المستخدم، الفرع والوتيرة؛ لن تُرفع تغييرات أثناء تقرير المراجعة.

## 12. ملحق حالة التنفيذ المحلي — 28 أكتوبر 2026

هذا الملحق أحدث من أوصاف الحالة في الأقسام السابقة، ويُقرأ معها لتحديث التقدم فقط؛ لا يغيّر حدود المراجعة ولا يعني اكتمال النظام أو اختباره في الإنتاج.

### ما أُنجز محليًا منذ النسخة الأساسية

- **Lineage وهوية الرمز:** يرسل الجسر `provider`, `broker`, `server`, `raw_symbol`, `logical_symbol` وهوية `source_id`. تُبنى هوية المصدر من المزود/الوسيط/الخادم/الرمز الخام، لا من alias المنطقي، لتظل مستقرة عند إعادة ربط alias. مواصفات العقد تحفظ في `contract_snapshots` مع `observed_at` و`spec_json`، ويرتبط snapshot بصفوف ticks/bars. استعلامات DuckDB تعيد حقول الهوية ولا يزيل dedup صفوف مصادر أو رموز خام مختلفة. هذا يحفظ الهوية قبل/بجانب التوحيد المنطقي، لكنه لا يقرر أن أصلين مختلفين متكافئان.
- **ticks:** يستخدم الجسر `copy_ticks_range` بدفعات وwatermark واستردادًا متداخلًا، مع batch/chunk metadata وإقرار قبل تقدم watermark. توجد حماية idempotency ومعاملة حفظ. لا يُدّعى اكتمال سجل الوسيط؛ اختبار الانقطاع/الاستعادة على MT5 Demo والتكامل الحي ما زالا مطلوبين.
- **training leakage:** حُفظ تعريف الهدف للشمعة المجاورة التالية، واستبعاد الميزات السعرية الخام/الهدف، والتحقق من السجلات القديمة. صار purge يستخدم `target_timestamp` الفعلي مع gap اختياري، مع تمرير أوقات الهدف من التدريب.
- **الأخبار/الاقتصاد:** تُسجل revisions التقويم الواردة في جدول DuckDB append-only مع `available_at` و`revision_id`. ميزات التقويم تستبعد ما لم يكن متاحًا عند القرار وتكتب provenance في سجل التدريب؛ السجل ذو ميزات التقويم دون receipt صالح يُرفض. هذا لا يغطي بعد مصادر الأخبار أو الأساسيات أو الأصول المرتبطة الأخرى، ولا يعوض غياب وقت النشر الحقيقي من المصدر.
- **دورة النموذج:** التدريب اليدوي والآلي ينتجان candidates بملفات receipt، ولا يستبدلان champion ولا يعيدان تحميل المرشح تلقائيًا. الترقية منفصلة ومحروسة بمتغير `NEXUS_ML_PROMOTION_TOKEN` وعبارة تأكيد صريحة، مع حفظ الإصدارات السابقة. لا يوجد حتى الآن مسار dataset مستقل لتدريب CSV/التاريخ؛ التدريب الحالي مصدره سجل Redis الحي فقط.
- **التقييم والتكاليف:** أضيفت مدخلات spread/commission/fees/slippage، وفصل `gross_pnl` عن `net_pnl` وتوثيق افتراضات المحاكي. القيم الافتراضية لا تكفي لادعاء أداء تداول واقعي دون معايرة وبيانات bid/ask تاريخية.

### الاختبار والحدود الحالية

اجتازت ملفات Python ذات الصلة `compileall` و`git diff --check`، واجتازت اختبارات `unittest` المتاحة لبيانات التدريب. نجحت smoke checks لـPIT التقويم وpurge والتكاليف. لم يُشغّل MT5 حي أو Demo، ولم يُنفذ تدريب فعلي أو ترقية نموذج. كل التعديلات محلية؛ لم يحدث commit أو push.

## 13. تحديث اختبارات السببية وبيانات الأخبار — 28 أكتوبر 2026

- أُضيف closed-bar filter إلى معالجة feature stream وendpoint الحساب ad-hoc: ترتيب زمني، إسقاط التوقيت المفقود، واستبعاد أي شمعة لم يكتمل interval الخاص بها. كما صار `aggregate_features` في MTF يقبل `as_of`، يرتب الصفوف، ويعيد فقط bars المغلقة قبله مع وقت bar المختار.
- توسع prefix test القياسي إلى 240 شمعة لاختبار مؤشرات warm-up الطويلة، وأضيف `test_extended_prefix_causality.py` لاختبار MTF، بوابة الشموع المغلقة، تأخر تأكيد swing/S-R levels ووقت توفر order blocks، وsnapshot calculations للأصول المرتبطة والمؤشرات المؤسسية.
- صارت استجابات swing/order-block تحمل `confirmation_index` و`confirmed_at`؛ هذا يمنع تفسير مستوى اكتُشف لاحقًا على أنه كان معلومًا عند شمعة الأصل.
- أُضيف `available_at`, `event_id/revision_id` إلى نماذج NewsItem/CalendarEvent، مع content-addressed revision IDs وتقويم الخدمة يحتفظ بأول observed time أثناء بقاء الإصدار معروفًا في الذاكرة. هذه ليست أرشفة تاريخية دائمة؛ snapshots الأخبار/تقويم الخدمة لا تزال غير append-only بعد إعادة التشغيل، فلا يجوز بناء backtest تاريخي منها.
- eligibility للتدريب يطلب receipt لكل ميزات `cross_asset`, `news`, `sentiment` و`macro/economic/fundamental`؛ يشترط وقت قرار مطابقًا و`available_at <= decision_time` وهوية مصدر وإصدار. المصادر التي لا تملك archive/vintage لا تدخل التدريب بأمان؛ يبقى توصيل loader تاريخي إلى مصدر إصدارات دائم مطلوبًا.

### تحقق هذا التحديث

نجح `compileall` و`git diff --check`، ونجحت 13 اختبارات بيانات تدريب و8 اختبارات خصائص causal و5 اختبارات metadata للأخبار/التقويم بالتشغيل المباشر. لم تتوفر `pytest`، لذا لم تُنفذ pytest suite كاملة. بعض مكتبات Hurst/entropy/matrix-profile/change-point غير مثبتة في `.venv`؛ لذلك تعتمد تلك الفروع graceful defaults في اختبار snapshots، ولا تعني النتائج التحقق العددي من implementations الاختيارية.
